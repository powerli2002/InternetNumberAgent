# Harness 编程规范

## 为什么要做 Harness

对于 Coding Agent，真正稀缺的不是“规则数量”，而是高质量、可验证、可维护的上下文。把所有规则堆进 `AGENTS.md` 往往会带来三个问题：
- 上下文被旧说明和噪声挤占。
- AI 很难判断哪份信息是当前权威。
- 文档逐渐腐烂，最后变成无法验证的经验堆。

因此，本仓库采用“薄入口 + 结构化文档 + 定期清理”的 Harness 方案。

## 本仓库的 Harness 原则

### 1. 薄入口
- 根目录 `AGENTS.md` 只保留硬约束、目录索引和最低限度的决策规则。
- 详细知识不再堆在 `AGENTS.md`，统一沉到 `docs/`。

### 2. 单一权威文档
- 一个主题只保留一份当前权威文档。
- 同类信息不能长期散落在多个当前文档中。
- 历史内容统一转入 `docs/90-archive/`。

### 3. 先让人理解，再让 AI 执行
- 文档结构先服务系统理解，再服务具体开发和运维，最后服务 AI 规则。
- AI 入口文档应该能明确告诉模型“这次任务先读什么”。

### 4. 以代码为准
- 当文档和代码冲突时，以代码实现为准。
- 但不能止步于“知道冲突”，必须在同次任务里修正文档。

### 5. 抗熵
- 过期文档不是留着不动，而是修、归档或删。
- 历史方案可以保留背景价值，但必须退出主文档区。

## AI 工作流建议
1. 读取 `AGENTS.md` 和 `docs/README.md`。
2. 根据任务进入对应权威文档。
3. 再去读代码，而不是先在仓库里盲搜所有旧文档。
4. 修改完成后回写相关文档正文。
5. 发现旧文档冲突时，同步清理到 `docs/90-archive/`。

## 不推荐的做法
- 把所有知识继续堆回 `AGENTS.md`
- 通过新建“补充说明”“更新记录”“修复说明 2”来覆盖旧文档
- 让过期文档继续停留在主文档区
- 让 AI 同时依赖多份相互矛盾的当前文档

## 适用于本仓库的实践要求
- 数据模型、运行命令、部署步骤必须有明确权威文档。
- 面试型、历史型、实验型材料默认进入归档区。
- 文档修改采用直接重写正文，而不是追加变更日志段落。
