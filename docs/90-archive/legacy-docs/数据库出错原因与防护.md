# PostgreSQL 数据损坏原因与防护措施

## 一、现象回顾

- PostgreSQL 启动失败，日志提示无法找到或读取 `pg_control`/`pg_xact` 等关键文件。
- 数据目录缺失关键文件，导致容器无法恢复已存在的数据实例。

## 二、根因分析

1. **数据目录被误挂载到空路径**  
   当 `docker-compose.yml` 从项目根目录迁移到 `docker/` 目录后，如果仍使用 `./mount/pgdata`，会被解析到 `docker/mount/pgdata`（空目录），导致 PostgreSQL 以空目录初始化或直接报错。

2. **迁移/重命名目录时未先停止容器**  
   在容器运行期间移动或删除数据目录，可能造成 `pg_control` 等文件缺失或写入不完整，最终触发损坏。

## 三、已采取的修复

- **统一挂载路径**：`docker/docker-compose.yml` 中所有数据卷改为 `../mount/...`，确保无论 compose 文件位置如何变化，都挂载到项目根目录的 `mount` 目录。
- **配置集中管理**：将 `config.yaml`、`config.docker.yaml`、`.env`、`milvus.yaml` 统一移动到 `conf/`，减少路径漂移导致的误挂载风险。

## 四、防护与操作建议

1. **迁移数据前必须停容器**  
   先执行 `docker compose -f docker/docker-compose.yml down`，确认容器停止后再移动 `mount/pgdata`。

2. **迁移使用保真拷贝**  
   推荐使用 `rsync -a` 或 `cp -a`，确保 `PG_VERSION`、`global/pg_control` 等文件完整保留。

3. **启动前检查数据目录完整性**  
   确认 `mount/pgdata` 下存在 `PG_VERSION`、`base/`、`global/`、`pg_wal/` 等关键目录后再启动服务。

4. **固定使用统一的 Compose 入口**  
   统一使用 `docker/docker-compose.yml` 启动服务，避免不同入口造成路径误用。
