## 1. 概述

互联网号码资源（Internet Number Resources, INR）涵盖 AS（自治系统号）、IP 前缀、组织与国家等实体，背后分布在 RIR 委托、WHOIS/RDAP 注册信息、BGP 路由观测与 DNS/网站解析等数据源中。业务场景需要把这些碎片化数据融合为可检索的知识图谱与结构化数据库，以支撑实时问答、归属分析与风险追踪。

本项目的目标是构建一个“互联网号码资源问答系统”的 MVP：以融合处理层为基础，将多源数据清洗、对齐、实体化写入 PostgreSQL；同时构建向量检索（Milvus）与语义图谱（Neo4j）两类记忆系统；通过智能体层（FusionAgent）把 NL2SQL、RAG 与记忆机制结合起来，形成可解释的问答链路与可观察的运行过程。

面向新用户，本系统可用于以下典型场景：
- **网络资产归属**：输入 IP/ASN，追溯所属组织、国家与路由归属差异（注册 vs 观测）。
- **拓扑与运营分析**：对 AS 上下游、对等关系与前缀分布进行快速检索与解释。
- **安全与治理**：识别异常归属、跨地域路由漂移、组织关联关系等。
- **运维知识库**：将项目文档、操作手册与业务笔记索引为向量库，支持自然语言检索。

系统设计强调“工程可落地”和“可解释性”：核心数据保留在 PostgreSQL，检索与推理逻辑清晰可追踪；记忆与上下文构建可复用 Hello‑Agents 的最佳实践；监控采用 LangSmith 统一采集 LLM、工具调用与链路指标。

### 1.1 术语与缩写

为便于新读者理解，以下是文档中频繁出现的术语解释：

- **AS / ASN**：自治系统及其编号（Autonomous System Number）。
- **Prefix**：IP 前缀，例如 `1.2.3.0/24`；在图谱与查询中统一使用前缀而不是单点 IP。
- **RIR**：区域互联网注册机构（Regional Internet Registry）。
- **WHOIS / RDAP**：注册信息协议，RDAP 为 WHOIS 的现代化实现。
- **BGP**：边界网关协议，提供路由与拓扑观测。
- **RAG**：检索增强生成（Retrieval‑Augmented Generation）。
- **NL2SQL**：自然语言到 SQL 的转换与执行流程。
- **GSSC**：上下文工程流程（Gather/Select/Structure/Compress）。

### 1.2 设计原则

系统在工程实现中遵循以下原则：

1) **结构化数据优先**：以 PostgreSQL 作为事实源，所有派生索引（Milvus/Neo4j）均可从结构化表重建。
2) **幂等与可重复**：导入脚本与图谱构建保证可重复执行，避免重复写入与不可控状态。
3) **证据驱动**：答复包含可溯源的证据（SQL 结果、文档片段、图谱关系）。
4) **可观测性**：链路追踪覆盖 LLM 与工具调用，便于定位错误与性能瓶颈。

### 1.3 稳定性修复说明（2026-02-08）

本次版本在“编排鲁棒性、语义记忆、NL2SQL 超时治理”上完成了关键修复：

1. **语义记忆可用性**：修复 Neo4j map 属性写入错误，改用 `metadata_json/source/category/importance/tags` 存储。
2. **Todo 解析兼容性**：支持 `subtasks/items/todos/plan` 多种 LLM 返回结构，减少兜底退化。
3. **图谱查询鲁棒性**：增加 Cypher 关系白名单校验，关系越界时自动回退到安全模板查询。
4. **NL2SQL 超时退化**：当列检索阶段超时，自动降级为表级检索重试，提升任务完成率。
5. **RAG 增量去重**：向量写入前按 `source + text` 进行哈希去重，避免重复切片污染索引。
6. **示例路径对齐**：补齐 `agent/knowledge/bgp/hijack_detection.md`，chapter_5 的示例命令可直接执行。

## 2. 整体架构

### 2.1 分层架构总览

系统采用分层架构，将离线数据处理与在线问答解耦：

1) **数据处理层**：对 RIR/WHOIS/RDAP、BGP 路由、DNS/网站信息进行清洗、实体化、字段标准化与多值解析，生成 16 张核心表 CSV。  
2) **结构化存储层**：PostgreSQL 作为权威数据源，承载 16 张核心实体表，保证查询稳定与可审计。  
3) **向量与记忆层**：Milvus 负责文档向量索引；Neo4j 负责语义图谱与概念记忆。  
4) **上下文工程层**：基于 GSSC（Gather/Select/Structure/Compress）组织上下文，将证据与历史有序注入。  
5) **对话代理层**：FusionAgent 负责路由 NL2SQL / RAG / 记忆 / 子任务，实现“检索 + 生成 + 归因”的闭环。

### 2.3 关键组件与交互

- **FusionAgent**（`agent/runtime/fusion_agent.py`）：主代理入口，负责任务理解、Function Calling 路由、上下文构建与回答生成。
- **MCPToolClient**（`agent/services/mcp/client.py`）：主代理统一通过该客户端调用 FastMCP 工具服务。
- **FastMCP Tool Server**（`agent/services/mcp/server.py`）：暴露 `nl2sql_query/rag_search/neo4j_llamaindex_query/note_search/todo_*` 工具。
- **LangGraphOrchestrator**（`agent/runtime/langgraph_orchestrator.py`）：主编排图（计划、分发、并行执行、冲突核验、重规划），状态模型采用 `MessagesState + 业务字段`，其中 `messages` 是唯一对话真相源；项目主 HTTP 运行链路编译图时挂载 `PostgresSaver`，通过 LangGraph 原生 `thread_id`/checkpoint 持久化线程状态；`langgraph dev` / Studio 入口则关闭自定义 checkpointer，改用 LangGraph API 自带 persistence，避免图加载失败；流式输出使用 `graph.stream(..., stream_mode=["custom", "updates"])`，由 `generate_answer` 节点通过 `get_stream_writer()` 直接发出增量回答。`respond/stream_response` 外层统一使用 4 层 Turn Middleware：`TurnSetup`、`TraceScope`、`NodeAudit`、`Finalize`，负责 thread/trace 准备、LangSmith 作用域、节点审计容器与统一收尾，不改变图内节点执行顺序。
- **MemoryManager**（`agent/memory/manager.py`）：统一管理工作记忆、情景记忆与语义记忆。
- **ContextBuilder**（`agent/runtime/context_builder.py`）：GSSC 上下文组装器。
- **LangSmithTracer**（`agent/core/tracing.py`）：LangSmith 配置加载与默认 metadata/tags 生成。

### 2.4 核心数据流

1) 数据融合脚本将 CSV 落地 PostgreSQL（或先落库再入图谱）。
2) 文档、技能与笔记形成向量索引（Milvus）。
3) 用户提问 → FusionAgent（LangGraph）：
   - 输入状态以 `messages` 作为唯一对话状态，可由 LangGraph Studio/Chat mode 直接驱动；
   - HTTP 层只负责线程注册与 metadata，历史消息与图状态由 LangGraph `PostgresSaver` 通过 `thread_id` 持久化；
   - turn 入口先经过 `TurnSetup -> TraceScope -> NodeAudit -> Finalize` 四层 Middleware，统一管理单轮生命周期与追踪收尾；
   - `reset_turn_state`：新 turn 入口先清空上一轮遗留的 `step_results/evidences/context/conflicts` 等易变执行态。
   - `plan`：生成执行计划（步骤、依赖、工具）。
   - `dispatch/execute`：按依赖调度，简单步骤并行调用 MCP（`nl2sql/rag/neo4j_llamaindex_query`），复杂步骤进入 `todo_subgraph`。
   - `conflict_check/replan`：冲突核验后按需局部重规划。
4) ContextBuilder 组织上下文 → `generate_answer` 节点流式生成答复，并同步写入记忆与 LangSmith。

## 3. 数据与实体关系

### 3.1 数据来源与实体范围

系统数据来自多源融合：
- **RIR 委托数据**：提供 AS/前缀/组织基础信息与注册归属。
- **WHOIS/RDAP 数据**：补充注册信息、联系人与机构字段；RDAP 是 WHOIS 的现代化协议实现。
- **BGP 观测数据**：提供前缀到 ASN 的观测归属与路由拓扑关系。
- **DNS/网站解析**：将域名、网站与 IP/前缀关联起来。

实体建模以 **AS、Prefix、Org、Country** 为核心，IP 单点不作为图谱节点，统一以 Prefix 表示；Registry 相关信息（inetnum/rdap/route）作为 Prefix 的属性保存，避免拆分成额外节点。

### 3.2 16 张核心表与用途

> 数据来自 `summary.md` 约定，导入时以表名为固定名称（不带日期），CSV 文件多带日期后缀。以下为“表名/用途/关键字段/关系”的最小说明。

| 表名 | 主要用途 | 关键字段示例 | 关系与映射 |
| --- | --- | --- | --- |
| as_entity | AS 画像融合 | asn, aut_name, org_id, org_name, v4peer | AS ↔ Org / Country / Prefix / AS 拓扑 |
| asn_entity | ASN 委托基础 | asn, org_name, country | AS ↔ 委托来源 |
| country_entity | 国家统计 | country, asns_number, v4prefixes_number | Country ↔ AS/Org/Prefix |
| industry_entity | 行业网站画像 | url, industry, ip_asn | Website/Org/AS 关联 |
| ip_bgp_entity | IP 前缀 BGP 归属 | prefix, route, bgp, org_uuid | Prefix ↔ AS/Org/ Country |
| ip_inetnum_entity | IPv4 WHOIS 信息 | cidr, netname, org | Prefix Registry 属性 |
| ip_rdap_entity | IPv4 RDAP 信息 | cidr, netname, org | Prefix Registry 属性 |
| ip_route_entity | IPv4 ROUTE 信息 | cidr, origin, mnt_by | Prefix Registry 属性 |
| ipv4_entity | IPv4 委托 | prefix, org_id, sibling_as | Prefix ↔ Org/AS |
| ipv6_bgp_entity | IPv6 BGP 归属 | prefix, route, bgp | Prefix ↔ AS/Org |

| ipv6_rdap_entity | IPv6 RDAP | cidr, netname | Prefix Registry 属性 |
| ipv6_route_entity | IPv6 ROUTE | cidr, origin | Prefix Registry 属性 |

| website_entity | 网站基础信息 | url, ip, ip_prefix | Website ↔ Prefix/AS |

### 3.3 字段预处理规则

为了保证下游查询稳定性，字段需要做一致化处理：

1) **多值字段解析为数组**：如 `v4peer`、`sibling_as`、`geo_country_list` 等，CSV 中通常为 Python 列表字面量字符串，应解析为数组类型（`text[]`/`bigint[]`）。
2) **JSON 字段**：`admin_info/tech_info/abuse_info` 为 JSON 字符串，落库为 `json` 或 `jsonb`。
3) **前缀字段**：统一使用 `cidr/inet` 表示；与 `prefix_len` 形成一致规则。
4) **空字段处理**：空字符串或 `[]` 统一视为缺失，避免写入无效值。
5) **列名规范化**：导入时统一将列名转换为 `lowercase + underscore`（如 `v4Prefixes -> v4prefixes`、`CIDR -> cidr`、`admin-c -> admin_c`），减少 SQL 大小写与特殊字符引用错误。

示例解析逻辑（伪代码）：

```python
# 解析多值字段与 JSON 字段（示意）
import json
import ast

def parse_array(value: str):
    if not value or value == "[]":
        return []
    return ast.literal_eval(value)

def parse_json(value: str):
    if not value:
        return {}
    return json.loads(value)
```

### 3.4 实体关系抽取与映射

系统主要使用如下映射规则构建实体关系：

- **AS ↔ Org**：`as_entity.uuid` ↔ `org_entity.uuid`；AS 的组织信息可从 `org_handle/org_id` 或 `org_uuid` 关联。
- **Prefix ↔ AS（注册/观测）**：`ip_bgp_entity.route` 表示注册归属 ASN；`ip_bgp_entity.bgp` 表示 BGP 观测 ASN，用于一致性比对。
- **Prefix ↔ Org**：`org_uuid_prefix/org_uuid_bgp` → `org_entity.uuid`。
- **Prefix ↔ Country**：`ip_bgp_entity.country` → `country_entity.country`。
- **IPv4/IPv6 委托 ↔ Org/AS**：`ipv4_entity/ipv6_entity` 的 `uuid` 与 `sibling_as` 等字段与 `org_entity/as_entity` 关联。
- **Registry 属性**：inetnum/rdap/route 信息写入 Prefix 的属性字段或 Registry 段落，避免单独建节点。

上述映射为后续图谱导入与 NL2SQL 查询提供统一视图，使查询路径稳定可控。

### 3.5 多值字段解析与实体映射示例

**多值字段解析**（以 `sibling_as`、`v4peer` 为例）：

1) CSV 中常见格式为字符串形式的列表，例如 `"[123, 456, 789]"`。
2) 解析后写入 PostgreSQL 的数组类型字段，以便使用 `ANY()` 与数组函数进行查询。
3) 空数组统一写入 `[]`，避免空字符串带来的不一致。

**实体映射示例**（Prefix → AS → Org → Country）：

```sql
-- 以 IP 前缀为起点，关联 ASN、组织与国家
SELECT
  p.prefix,
  p.bgp AS asn_observed,
  a.org_name,
  c.country_cn
FROM ip_bgp_entity AS p
LEFT JOIN as_entity AS a ON p.bgp = a.asn
LEFT JOIN country_entity AS c ON p.country = c.country
WHERE p.prefix = '1.2.3.0/24';
```

该链路是“号码资源归属”查询的核心路径；在图谱中对应 `IPPrefix -[:OBSERVED_BY]-> AS -[:BELONGS_TO]-> Org -[:LOCATED_IN]-> Country` 的关系链。

## 5. 向量索引与 NL2SQL

### 5.1 LlamaIndex 在 NL2SQL 中的作用

系统将 LlamaIndex 作为 NL2SQL 的“解释与生成引擎”，负责：
1) 从 `SQLDatabase` 读取数据库结构；
2) 使用 LLM 生成 SQL；
3) 结合嵌入模型与表结构上下文增强匹配准确率；
4) 查询时表检索（`SQLTableNodeMapping` + `ObjectIndex`）自动筛选相关表；
5) 查询时列检索：为指定列构建离散值索引，补全可用的枚举取值。

在本项目中，NL2SQL 的核心流程为：
`question → SQLTableRetrieverQueryEngine → SQL → PostgreSQL → result`。表结构信息来自 `agent/core/schema.py`，通过 `context_query_kwargs` 注入 LLM 提示中，并结合表/列检索提升生成准确率。

### 5.2 LLM 与 Embedding 调用规范

LLM 通过统一 OpenAI 兼容接口访问后端（`LLM_BACKEND=cloud|local`）；RAG/NL2SQL 的 embedding 默认使用本地离线 bge（可切换为 DashScope）：
- `agent/core/llm.py`：用于普通对话；
- `agent/tools/nl2sql_tool.py`：面向 LlamaIndex 的 Custom LLM 与 Embedding 适配（NL2SQL 默认本地 bge）；
- `agent/tools/rag_tool.py`：面向向量检索的 Embedding 适配（默认本地 bge，支持切换）。

本地 embedding 实现口径已统一为 `HuggingFaceEmbedding`，避免 RAG 与 NL2SQL 使用不同本地推理栈导致行为不一致；两者 Milvus 存储保持分离：`fusion_docs`（RAG）与 `nl2sql_index`（NL2SQL）。

当前默认温度策略也按任务类型拆分：
- `LLM_TEMPERATURE=0.2`：普通文本生成，覆盖最终回答、普通 `chat` 与 `structured_chat`。
- `LLM_TOOL_TEMPERATURE=0.0`：强约束调用，覆盖 planner 的 function calling、冲突判定、NL2SQL SQL 生成与 Neo4j Text2Cypher。
- `LLM_CONTEXT_COMPRESS_TEMPERATURE=0.0`：上下文压缩，要求在 token 预算内尽量保真。

**关键注意**：RAG 与 NL2SQL 的 embedding 默认都不依赖在线 embedding key；仅在 `*_EMBEDDING_BACKEND=dashscope` 时才会调用 `DASHSCOPE_EMBEDDING_MODEL`。

### 5.2.1 LLM 后端路由机制与失败策略

1) 配置解析入口是 `agent/core/config.py`。系统先读取 `LLM_BACKEND`，再按后端读取对应环境变量：  
- `cloud`：`DASHSCOPE_API_KEY`、`DASHSCOPE_BASE_URL`、`DASHSCOPE_MODEL`  
- `local`：`LOCAL_LLM_API_KEY`、`LOCAL_LLM_BASE_URL`、`LOCAL_LLM_MODEL`

2) 解析逻辑在 `agent/model/llm_endpoint.py`，只返回一个“当前生效端点”（`api_key/base_url/model`），再写回统一字段供全链路复用（主 Agent、MCP、评测）。

3) 失败策略是“显式失败”：  
- `LLM_BACKEND` 非法值：直接抛错；  
- 关键字段缺失：直接抛错；  
- 不做 cloud/local 自动回退，避免误连错误模型或错误环境。

### 5.3 构建向量索引（Milvus）

### 5.5 NL2SQL 安全与可控执行

为降低 NL2SQL 的执行风险，系统增加了 SQL 安全守卫与执行限制：

- **只读限制**：仅允许 `SELECT/CTE` 查询，禁止写操作与危险关键字。
- **表白名单**：仅允许访问 16 张核心表，避免越权查询。
- **步骤级缩表**：planner 为每个 `nl2sql` 步骤单独下发 `tables` 子集，SQL 生成 prompt 中的 `{schema}` 仅包含该子集；未出现在 `{schema}` 的表禁止出现在 SQL 中。
- **强制 LIMIT**：所有 SQL 自动添加/收敛 `LIMIT`（默认 200 行）。
- **超时控制**：执行时设置 `statement_timeout`（默认 15000ms）。
- **子查询策略**：默认禁止子查询（可通过环境变量开启）。
- **规划驱动意图位**：`query_mode=COUNT/GROUP_BY/EXISTS/OTHER` 由 planner 一次性给出，execute/MCP/NL2SQL 仅透传消费。
- **提示词引导聚合**：审计/对比/存在性问题通过 `query_mode` 驱动 SQL 生成形态，不再做执行期硬拦截与重生。
- **数组列约束**：对 `text[]` / `bigint[]` 数组列，prompt 明确禁止与标量列直接做 `=` JOIN，需使用 PostgreSQL 合法数组谓词。

可通过环境变量调整：

```dotenv
NL2SQL_MAX_ROWS=200
NL2SQL_STATEMENT_TIMEOUT_MS=15000
NL2SQL_MAX_SQL_LENGTH=4000
NL2SQL_ALLOW_SUBQUERY=false
```

MCP `nl2sql_query` 关键参数：

- `query_mode`：`COUNT/GROUP_BY/EXISTS/OTHER`
- `intent_policy`、`intent_labels_required`：兼容字段（deprecated，不参与逻辑判断）

返回 `result` 中新增以下可观测字段：

- `metadata.query_mode`
- `metadata.generation_mode=planner_driven`

### 5.6 向量检索参数与召回策略

当前 Milvus 索引由 `RAGTool` 自动创建，默认配置为：

- 索引类型：`IVF_FLAT`
- 相似度指标：`COSINE`
- `nlist=128`
- 搜索参数：`nprobe=10`

向量字段为 `embedding`，文本字段为 `text`，来源字段为 `source`。系统首次写入时自动探测 embedding 维度并初始化集合；若集合维度与当前模型不一致，会直接报错并提示重建索引，避免“旧向量 + 新模型”混用。

当前默认召回策略为 **MQE + RRF**：

- RRF：融合多个查询的排序结果；
- 最终返回 Top-K 去重片段。

## 6. 记忆与上下文管理

### 6.1 三类记忆的职责划分

系统将记忆分为三类，并由 `MemoryManager` 统一调度：

| 记忆类型 | 位置 | 作用 | 检索方式 |
| --- | --- | --- | --- |
| 工作记忆 | 内存 | 保存短期对话与证据片段 | 关键词 + 简单评分 |
| 情景记忆 | PostgreSQL（`agent_episodic_memory`，默认；无 PG 时回退 SQLite） | 保留重要会话片段与工具结果 | 关键词检索 |
| 语义记忆 | Neo4j | 保存长期知识与概念关系 | 图检索 / 属性匹配 |

情景记忆默认写入 PostgreSQL 的 `agent_episodic_memory` 表（首次运行自动建表）；若未配置 `POSTGRES_URL`，则回退使用本地 SQLite 文件 `agent/store/memory/episodic.sqlite`。
语义记忆在 Neo4j 不可用时会自动降级为 no-op（不阻断主流程），并在日志记录告警。

这一分层设计与 Hello‑Agents 的记忆系统架构一致，强调工作/情景/语义多层协作与可扩展性。

### 6.2 MemoryManager 的写入与检索策略

`FusionAgent` 在工具调用后将结果写入记忆：
- NL2SQL 结果 → 情景记忆；
- RAG 文档片段 → 工作记忆；
- 图谱知识或稳定概念 → 语义记忆（Neo4j）。

同时，系统在生成最终回答后会触发**语义记忆抽取**：从“用户问题 + 回答”中提取稳定的概念、规则或偏好，写入 Neo4j 的 `Concept` 节点，避免语义记忆长期为空导致检索无效。

检索时，`MemoryManager.search()` 会合并三类记忆并按评分排序，保证与当前问题最相关的内容优先进入上下文。

### 6.3 GSSC 上下文工程

ContextBuilder 的核心流程为 Gather → Select → Structure → Compress，并对应以下行为：
- **Gather**：收集系统提示、用户问题、历史对话、记忆与证据；
- **Select**：按评分排序选取高价值片段；
- **Structure**：按模板分区组织上下文；
- **Compress**：仅当结构化上下文超过 `max_tokens` 时才调用 LLM 压缩；压缩前先拆分 `Evidence` 与 `Other` 两桶分别处理，若单桶输入超出单次请求窗口，则按分块多次调用 LLM 后回拼。

当前实现还补充了两条关键约束：
- `build_context` 优先使用当前轮 `step_results` 重建结构化证据，不再优先依赖 `execute_ready` 中写入的 evidence preview，避免 SQL/图查询结果在进入上下文前被二次截断。

压缩策略新增配置：
- `CONTEXT_COMPRESS_MODE` 为兼容保留字段，当前固定按 `llm` 处理；
- `CONTEXT_COMPRESS_TARGET_RATIO`（默认 `0.7`）。
- `LLM_CONTEXT_COMPRESS_TEMPERATURE`（默认 `0.0`，压缩任务优先保留实体、数字与证据线索）。

该流程与 Hello‑Agents 的上下文工程设计一致，可视为 GSSC 的工程化实现。

### 6.4 上下文结构模板

当前模板分区为：`Role & Policy`、`Task`、`Evidence`、`Context`、`Output`。这确保系统提示与证据优先级最高，历史对话与记忆作为上下文补充进入模型。

### 6.4.1 本机 vLLM 启动说明（Qwen3.5-4B 4-bit AWQ）

当前项目默认本机模型已切换为 `QuantTrio/Qwen3.5-4B-AWQ`（基于 `Qwen/Qwen3.5-4B` 的 4-bit AWQ 量化版本）。`agent/model/start_vllm.py` 的默认行为如下：

- 启动脚本会先读取 `conf/.env`，默认继承 `LOCAL_LLM_MODEL`、`LOCAL_LLM_API_KEY`、`LOCAL_LLM_BASE_URL`、`LOCAL_VLLM_MAX_MODEL_LEN`、`LOCAL_VLLM_QUANTIZATION`、`LOCAL_VLLM_DTYPE`、`LOCAL_VLLM_TENSOR_PARALLEL_SIZE`、`LOCAL_VLLM_CUDA_VISIBLE_DEVICES`。
- Agent 运行时还会从 `conf/.env` 读取 `LLM_TEMPERATURE`、`LLM_TOOL_TEMPERATURE`、`LLM_CONTEXT_COMPRESS_TEMPERATURE`，用于区分普通回答、工具决策与上下文压缩三类任务。
- 默认不显式透传 `trust_remote_code`，避免对已内置架构模型打印“参数无效”告警。
- 当模型名包含 `AWQ` 或环境变量显式设置 `LOCAL_VLLM_QUANTIZATION=awq` 时，启动脚本会追加 `--quantization awq`；若未额外指定 `dtype`，则自动使用 `--dtype half`。
- 当前默认配置为单卡推理：`LOCAL_VLLM_TENSOR_PARALLEL_SIZE=1` 且 `LOCAL_VLLM_CUDA_VISIBLE_DEVICES=0`，启动脚本会把 `CUDA_VISIBLE_DEVICES` 收敛到第 0 张卡。
- 当 `tensor_parallel_size > 2` 时，自动追加 `--disable-custom-all-reduce`，减少 4 张 `RTX 2080 Ti` PCIe 场景下的重复告警。
- 对 `Qwen3.5` 系列，额外默认追加 `--attention-backend TRITON_ATTN`、`--mm-encoder-attn-backend TRITON_ATTN`、`--language-model-only`、`--skip-mm-profiling`，并通过 `--default-chat-template-kwargs '{"enable_thinking": false}'` 默认关闭 thinking，避免本地 Agent 请求在服务端进入长 `<think>` 链路。
- `LOCAL_VLLM_MAX_MODEL_LEN` 同时控制 Agent 应用侧的上下文预算与 vLLM 服务端总窗口，项目已统一为单一配置源。
- 当前默认量化模型首次冷启动会先从 Hugging Face 下载约 `6.1GB` 权重；下载完成前，OpenAI 兼容接口不会开始监听 `127.0.0.1:2222`。

`Qwen3-4B` 与 `Qwen3.5-4B` 在当前项目中的观测差异如下：

| 维度 | `Qwen/Qwen3-4B` | `Qwen/Qwen3.5-4B` |
| --- | --- | --- |
| 模型架构 | `Qwen3ForCausalLM` | `Qwen3_5ForConditionalGeneration` |
| 默认模型名 | `Qwen/Qwen3-4B` | `QuantTrio/Qwen3.5-4B-AWQ` |
| 启动脚本额外参数 | 无 | `--quantization awq`、`--dtype half`、`--tensor-parallel-size 1`、`CUDA_VISIBLE_DEVICES=0`、`--attention-backend TRITON_ATTN`、`--mm-encoder-attn-backend TRITON_ATTN`、`--language-model-only`、`--skip-mm-profiling` |
| vLLM 引擎 `enable_prefix_caching` | `True` | `False` |
| 多模态编码器日志 | 无 | 会出现 `MMEncoderAttention` / `vit attention` 相关日志 |
| 老卡注意力后端 | 主文本注意力可正常选择兼容后端 | 在 `RTX 2080 Ti` 上会先探测 `FA2`，随后回退到 `TRITON_ATTN` |
| 首次冷启动耗时 | 相对较短（本机已缓存） | 首次需额外下载约 `6.1GB` 量化权重，启动明显更慢 |

### 6.5 记忆评分与衰减策略（当前实现）

记忆检索的评分逻辑以“关键词匹配”为基础，不同类型的记忆采用不同的衰减策略：

- **工作记忆**：对 query 进行分词（简单空格切分），按命中比例计算分数，返回 Top‑K。
- **情景记忆**：在关键词分数基础上引入时间衰减，越新的记录得分越高，衰减系数约为 `1 / (1 + age_hours/24)`。
- **语义记忆**：使用 Neo4j 进行概念名称与描述的包含匹配，适合稳定概念或知识条目的检索。

该实现简单可解释，适合作为 MVP 的基础策略；后续可替换为向量相似度或混合检索。

## 7. 工具与 LangGraph 编排设计

### 7.1 核心工具清单

| 层 | 组件 | 功能 | 典型输入 | 输出 |
| --- | --- | --- | --- | --- |
| MCP Server | `nl2sql_query` | 自然语言转 SQL 并执行 | question, tables, query_mode | sql, result |
| MCP Server | `rag_search` | 文档向量检索 | query, top_k | 文档片段 |
| MCP Server | `neo4j_llamaindex_query` | 自然语言图查询（工具内 Text2Cypher + 执行） | question, max_rows | cypher, rows |
| MCP Server | `note_search` | 笔记检索 | query, limit | notes[] |
| MCP Server | `todo_add/todo_list` | 待办写入/读取 | items | count/items |

### 7.2 LangGraph 调用策略

FusionAgent 当前使用 LangGraph 主图编排：

1) `reset_turn_state`：新 turn 入口显式清空上一轮遗留的 `step_results/evidences/context/conflicts` 等易变执行态，避免旧结果跨轮次污染后续节点；  
2) `plan`：动态探测可用工具能力，并通过 Function Calling 输出步骤计划（tool/arguments/depends_on）；重规划时会额外注入 `previous_plan_steps` 与 `previous_step_summaries`，用于避免重复步骤；  
3) `dispatch`：基于依赖关系挑选可执行步骤；  
4) `execute_ready`：并行调用 MCP 工具节点（`nl2sql/rag/graph`，其中 graph 默认走 `neo4j_llamaindex_query`）；同签名步骤（同工具+同目标+同参数）命中历史成功结果时直接复用，避免重复查询；  
   - `nl2sql/graph` 支持 `question` 或 `questions`（字符串数组）参数，数组模式按顺序逐条执行；若已提供 `question/questions`，执行层不再把 `objective` 自动追加成额外子问题；  
   - 若工具首次失败，会将首错信息注入重试上下文再执行一次（重试语义修正，不走静默降级）。  
5) `validate_plan`：会把“数量统计 + 前 N 示例”这类混合 NL2SQL 诉求拆成两个独立步骤，避免 count/list 混杂导致非法 SQL；  
6) `todo_subgraph`：仅在复杂步骤时展开子计划并执行；  
7) `conflict_check`：核验证据冲突，必要时触发局部 replan；  
8) `build_context/generate_answer`：统一构造上下文并生成最终回答；其中 `build_context` 优先消费 `step_results` 的结构化结果；当本轮计划为纯 `none` 时，主图会跳过数据工具与 note 检索，回答阶段改用 `system + 历史消息 + 当前 query` 的对话形式生成回复，而不是在回答节点直接短路；  
9) `write_memory`：写入 working/episodic/semantic 记忆。  

### 7.3 工具输入/输出约定与错误处理

- **输入约定**：MCP 输入为结构化 JSON，避免隐式协议。
- **输出约定**：所有工具结果统一映射为 `EvidenceItem + sources + result`。
- **错误处理**：节点级错误会写入步骤结果并继续流程，必要时触发重规划。

## 8. 监控与调试

### 8.1 启用 LangSmith 追踪

LangSmith 追踪通过环境变量开启，主要变量包括：
- `LANGSMITH_TRACING=true`
- `LANGSMITH_API_KEY=...`
- `LANGSMITH_WORKSPACE_ID=...`
- `LANGSMITH_PROJECT=internet-number-qa`
- `LANGSMITH_DEFAULT_TAGS=fusion,langgraph,mcp`

为确保 LLM 调用被记录，项目在 OpenAI 兼容客户端外包裹 `wrap_openai`，模型请求会自动进入 LangSmith 追踪树。

### 8.2 项目中的埋点方式

- `LangSmithTracer` 仅负责加载 LangSmith 配置，并统一生成默认 tags / metadata；
- FusionAgent 为每次提问创建一个 root run（`langgraph_agent`）；
- 主图状态继承 `MessagesState`，以 `messages` 作为唯一对话状态，并在 `generate_answer` 节点把最终回答追加回 `messages`；
- 图编译时挂载 `PostgresSaver`，每次请求通过 `configurable.thread_id` 进入 LangGraph 原生 checkpoint 流程；
- `graph.invoke(..., config={"configurable": {"thread_id": ...}})` 在 `tracing_context(parent=root_run)` 内执行，LangGraph 自动节点与 LLM run 归属同一 trace；
- 线程池执行步骤时显式继承 `contextvars`，保证并发步骤与 `todo` 子规划不会丢失父子关系；
- MCP 客户端仅透传 `get_current_run_tree().to_headers()` 生成的 LangSmith 分布式追踪头，不再手工创建客户端工具子 run；
- MCP 服务端通过 `TracingMiddleware + ls_trace()` 记录工具 span，并自动挂到当前 LangGraph 节点 run 下；
- 每个自动节点 run 直接写入 `inputs.state_snapshot / business_input / prompt_records / context_payload` 与 `outputs.state_update / business_output`，用于节点级审计回放；
- root run 输出保留 `trace_version`、`node_records`、`final_state_output`，用于兼容现有评测与导出脚本；
- tags 与 metadata 用于区分链路阶段与服务来源，方便后续聚合分析。

### 8.3 调试建议

- **LLM 调用失败**：检查 `conf/.env` 中 `DASHSCOPE_API_KEY` 是否生效，验证网络连通性。
- **NL2SQL 失准**：查看生成 SQL 与表描述是否匹配，必要时补充 `agent/core/schema.py` 的字段说明。
- **向量检索为空**：确认 Milvus collection 是否创建、向量维度是否一致、是否已插入数据。
- **图谱检索失败**：检查 Neo4j 连接、约束是否创建、是否完成图谱导入。

### 8.4 监控指标与仪表板建议

为了提升可观测性，可在 LangSmith 仪表板中重点关注以下指标：

- **链路耗时**：root run 的端到端耗时，以及自动节点/LLM run 的耗时分布。
- **工具成功率**：统计不同工具的成功/失败比例，快速发现故障点。
- **异常类型**：按错误类型聚合（SQL 语法、空结果、连接失败），便于定位瓶颈。
- **计划形态分布**：统计计划节点输出的步骤数量、工具组合与重规划次数，观察业务使用情况。

以上指标可用于定义告警阈值与优化方向，建议与项目日志结合使用。

### 8.5 后端请求日志

FusionAgent 的 API 层会记录请求与回复日志，便于排查问题与复现链路。日志默认写入：

### 8.6 OpenJudge 评测流水线（数据驱动）

为持续评估 FusionAgent 的稳定性与效果，项目在 `agent/evaluate/` 提供了可复现评测链路：

1) **生成 Query 数据集**：基于 `summary.md` 和内置题库模板生成 `queries.jsonl`，默认 30 题（`20 RAG + 5 NL2SQL + 5 Neo4j`）。  
2) **自动补齐 Answer**：调用 `FusionAgent.respond` 批量执行问题，写入 `answers.jsonl`，并按 `trace_id` 回拉 LangSmith root run，提取 `node_records/tool_calls/trajectory_messages` 等评测字段。  
3) **构造 Rubric 与 Grader**：使用 OpenJudge 的 `SimpleRubricsGenerator`（零样本）或 `IterativeRubricsGenerator`（标注驱动）生成 rubric；同时装配内置 Agent graders 与自定义 LLM graders。  
4) **执行评分与落库**：输出 `scored.jsonl`、`score_summary.json`、`manual_review.csv`，并可将结果推送到 LangSmith Experiment。  
5) **人工 Gold 转换**：人工修订 `gold.readable.yaml` 后转换为 `gold.jsonl`，仅用于数据驱动 grader 范例集（不作为答题链路输入）。

当前 `answers.jsonl` 除最终答案外，还会保留 `tool_execution_records`，按真实执行顺序记录 `step_id/name/arguments/status/error/result_preview`，用于后续工具链路评分。

当前仓库已附带起步题集：`agent/evaluate/data/queries_seed_30.jsonl`（兼容保留 `queries_seed_26.jsonl`）。

评分维度与权重：

- `reasoning_planning = grader(reasoning_planning)`  
- `tool_selection_accuracy = F1(expected_tools, actual_tools)`  
- `tool_argument_quality = ToolParameterCheckGrader(query, tool_definitions, tool_calls)`  
- `tool_outcome_effectiveness = TrajectoryComprehensiveGrader(query, trajectory_messages, answer)`  
- `tool_use_accuracy = 0.4*tool_selection_accuracy + 0.3*tool_argument_quality + 0.3*tool_outcome_effectiveness`  
- `final_response_quality = grader(final_response_quality)`  
- `evidence_groundedness = grader(evidence_groundedness)`  
- `overall = 0.15*reasoning_planning + 0.15*tool_use_accuracy + 0.35*final_response_quality + 0.35*evidence_groundedness`

说明：

- 对外 `overall` 仍保持 4 个主维度，便于与历史版本横向比较。  
- `tool_selection_accuracy` 只评价工具选择是否覆盖必要能力、是否引入无关工具；重复调用同一工具的影响交由参数与结果维度处理。  
- `tool_argument_quality` 关注参数是否从用户问题中正确抽取、类型是否合理、是否存在幻觉字段。  
- `tool_outcome_effectiveness` 从完整轨迹评估每一步工具调用对解题的贡献、相关性、准确性与效率。  
- `score_summary.json` 额外输出 `avg_tool_subscores` 与 `tool_subscore_weights`；`manual_review.csv` 也会展开三个工具子评分列。

常用命令：

```bash
python -m agent.evaluate.pipelines.generate_queries --count 30 --out agent/evaluate/data/queries.jsonl
# `fill_answers` 会自动开启 LANGSMITH_TRACING=true
python -m agent.evaluate.pipelines.fill_answers --in agent/evaluate/data/queries.jsonl --out agent/evaluate/data/answers.jsonl
python -m agent.evaluate.pipelines.build_graders --out agent/evaluate/data/rubrics.json
python -m agent.evaluate.pipelines.score_pipeline --in agent/evaluate/data/answers.jsonl --rubrics agent/evaluate/data/rubrics.json --out agent/evaluate/data/scored.jsonl --summary-out agent/evaluate/data/score_summary.json --manual-review-out agent/evaluate/data/manual_review.csv --push-langsmith --langsmith-mode writeback
# 对已完成的 answers.jsonl 执行后补工具重评分
python -m agent.evaluate.pipelines.score_pipeline --in agent/evaluate/data/answers.jsonl --rubrics agent/evaluate/data/rubrics.json --out agent/evaluate/data/scored.posthoc.jsonl --summary-out agent/evaluate/data/score_summary.posthoc.json --manual-review-out agent/evaluate/data/manual_review.posthoc.csv --posthoc-tool-rescore --posthoc-answers-out agent/evaluate/data/answers.posthoc.jsonl --push-langsmith --langsmith-mode writeback
python -m agent.evaluate.pipelines.convert_gold_readable --readable agent/evaluate/data/gold.readable.yaml --out agent/evaluate/data/gold.jsonl --base-gold agent/evaluate/data/gold.jsonl --answers agent/evaluate/data/answers.jsonl
python -m agent.evaluate.pipelines.build_graders --out agent/evaluate/data/rubrics.json --rubric-labeled-data agent/evaluate/data/gold.jsonl
```

一键执行：

```bash
# `run_pipeline` 会自动开启 LANGSMITH_TRACING=true
python -m agent.evaluate.pipelines.run_pipeline --count 30 --workdir agent/evaluate/data --push-langsmith
# 若需要在流水线末尾自动转换 gold：
# --gold-readable agent/evaluate/data/gold.readable.yaml --gold-out agent/evaluate/data/gold.jsonl --gold-base agent/evaluate/data/gold.jsonl
```

说明：重复执行 `--push-langsmith` 时，评测链路会按稳定 sample id 对 LangSmith dataset example 做 create/update 分流，保证脚本可重复执行。默认推荐 `--langsmith-mode writeback`：把本地已算好的分数直接写成 LangSmith run outputs + feedback，不再重复调用 grader；若需要保留旧式 LangSmith evaluator 行为，可显式使用 `--langsmith-mode evaluate`。

后补模式说明：

- `--posthoc-tool-rescore` 用于对已经生成好的 `answers.jsonl` 重新抽取工具链路字段，再按最新三个 tool grader 重算 `tool_use_accuracy` 与 `overall`。  
- `--posthoc-answers-out` 可选，用于把重建后的 `tool_execution_records / trajectory_messages / evidence_summary` 持久化到新的 answers 文件，便于复核。  

LangSmith 可视化建议：

1. 执行 `score_pipeline --push-langsmith` 后，从 `score_summary.json -> langsmith.experiment_url` 进入本次 Experiment。  
2. 在 Experiment 的 Feedback 面板按评分 key 过滤，重点查看 `overall_score`、`tool_selection_accuracy`、`tool_argument_quality`、`tool_outcome_effectiveness` 与 `tool_use_accuracy`。  
3. 点开单个样本后，在 Outputs 面板查看 `scores_raw`、`scores_dim`、`overall_score`、`score_reasons`，以及 `tool_execution_records`、`tool_calls`、`trajectory_messages`、`evidence_summary`，即可把分数与实际链路逐项对齐。  
4. 如需回看主 Agent 执行细节，可根据 `trace_id` 回到 LangSmith Trace 页面，联动查看 plan 节点、工具分发节点和 root run 输出。  

## 9. 示例与使用指南

### 9.1 数据导入（默认 PostgreSQL + Neo4j）

使用 Docker Compose 启动服务后，可执行 CSV 导入脚本：

```bash
# 方式一：本机手动执行脚本
python -m agent.scripts.load_all_csv --config conf/config.docker.yaml --root . --date 2024-08-12 --ensure-core

# 方式二：容器内手动执行脚本（无需本机 Python 依赖）
docker compose -f docker/docker-compose.yml run --rm agent-mcp \
  python -m agent.scripts.load_all_csv --config conf/config.docker.yaml --root /work --date 2024-08-12 --ensure-core
```

导入脚本应具备幂等性（重复执行不产生重复数据），并优先导入 16 张核心表。  
当前 `load_all_csv.py` 默认执行 PostgreSQL + Neo4j 双库导入，双库一致性机制为：PostgreSQL prepared transaction + Neo4j 单事务。Neo4j 失败会重试一次，重试耗尽后回滚到旧快照。

可使用以下命令关闭单事务（兼容大批量历史模式）：

```bash
python -m agent.scripts.load_all_csv --config conf/config.docker.yaml --root . --no-single-transaction
```

如需仅导入 PostgreSQL（不触发图导入），可追加 `--no-neo4j`：

```bash
python -m agent.scripts.load_all_csv --config conf/config.docker.yaml --root . --no-neo4j
```

若异常中断后需要排查 prepared 事务，可在 PostgreSQL 执行：

```sql
SELECT gid, prepared FROM pg_prepared_xacts;
COMMIT PREPARED '<gid>';
ROLLBACK PREPARED '<gid>';
```

### 9.2 图谱导入（Neo4j）

图谱导入脚本位于 `agent/scripts/neo4j_graph_loader.py`，可从 PostgreSQL 中抽取实体并写入 Neo4j：

```bash
# 默认导入（不包含网站/行业）
python -m agent.scripts.neo4j_graph_loader --batch-size 1000

# 跳过 AS 关系（如上游/对等）
python -m agent.scripts.neo4j_graph_loader --batch-size 1000 --skip-as-relations

# 单事务图谱导入（失败整批回滚）
python -m agent.scripts.neo4j_graph_loader --batch-size 1000 --single-transaction
```

注意：Registry 信息会作为 Prefix 属性写入，IP 单点不作为图谱节点。

### 9.3 向量索引构建

```bash

from agent.tools.rag_tool import RAGTool, DocumentChunk, build_rag_embedding

from pathlib import Path

    collection_name="fusion_docs",
```

### 9.5 常见问题与排查路径

| 现象 | 可能原因 | 排查建议 |
| --- | --- | --- |
| NL2SQL 报错或无结果 | 缺少表、字段描述不全 | 检查 `agent/core/schema.py` 与表是否存在 |
| RAG 检索为空 | 向量未写入或维度不一致 | 确认 Milvus 集合与 embedding 维度 |
| Neo4j 无数据 | 图谱导入未执行 | 运行 `neo4j_graph_loader` 并查看约束 |
| LLM 调用失败 | API Key 或网络问题 | 检查 `conf/.env` 与网络连通 |

这类问题建议优先从日志与 LangSmith trace 中定位具体环节，再进入数据库或索引层排查。
